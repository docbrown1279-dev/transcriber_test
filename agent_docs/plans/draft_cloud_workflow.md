
# Черновик облачного процесса разработки (Фаза A, ревизия 2)

**Статус:** draft, ждёт ✅.
**Решения пользователя учтены:** обмен идёт через `cloud_in/` → `cloud_out/`; правила для облачных агентов и все входные файлы кладутся в `cloud_in/` перед стартом этапа; путь указывается в промпте; в облаке LLM — Gemini, локально — Qwen; `eval/` снимается с трекинга.
**Связано:** [roadmap](draft_demo_roadmap.md), [стратегия тестирования](draft_test_strategy.md).

---

## 1. Механика обмена

Продуктовая разработка использует тот же плоский обменник, что исследование ([`future_research_rules.md`](../../docs/research_results/future_research_rules.md), правила `cloud-handoff` / `cloud-ingest`): облако читает **только** `cloud_in/`, пишет **только** `cloud_out/`, обменник перезаписывается на каждый handoff.

```
cloud_in/
├── HANDOFF.md            # текущий этап, ветка, «читать cloud_in → писать cloud_out»
├── prompt.md             # один промпт этапа (цель, шаги, шлюз, stop-list)
├── agent/                # роль облачного агента — стабильная между этапами
│   ├── AGENTS.md         # продуктовая роль: стек, бюджеты, запреты (образец — docs/research_results/AGENTS.md)
│   └── rules.md          # нормы кода/тестов/линта, запрет читать eval/ и .env
└── inputs/               # всё, что нужно этапу: аудио-клипы, артефакты-фикстуры, контракты, конфиги
```

`cloud_out/` — отчёт шлюза, метаданные прогона и всё, что этап должен вернуть отдельно от кода.

Код и тесты при этом остаются на своих местах (`src/`, `tests/`) — их облачный агент коммитит и **пушит ветку**; PR открывает локальный `./scripts/cloud_pr.sh`. `cloud_out/` — только отчёты прогона. Операционный гайд: [`manuals/cloud_flow.md`](../../manuals/cloud_flow.md).

## 2. Цикл одного этапа

```
локально (человек + @Planner)
  1. архив предыдущего prompt.md → prompts/{stage}_{дата}.md
  2. очистка cloud_in/ (кроме agent/) и cloud_out/
  3. pack: prompt.md + HANDOFF.md + inputs/ (копии, никогда originals из data/)
  4. commit + push ветки cursor/demo-d{N}-…
        ↓
облако (Cloud Agent, путь к cloud_in указан в промпте пользователя)
  5. preflight: проверить наличие всего из cloud_in/inputs/ и прочитать cloud_in/agent/
  6. установка окружения по agent/AGENTS.md → код в src/, тесты в tests/
  7. прогон шлюза этапа → cloud_out/gate_D{N}.md + cloud_out/run_meta.json
  8. commit + PR
        ↓
локально (человек)
  9. pull ветки, ingest: отчёты → agent_docs/reports/, прогресс → agent_docs/progress/
 10. ручной шлюз этапа на полной записи (см. §5) → PASS: merge; FAIL: правки промпта, новый прогон
```

Роли и границы не меняются: `@Coder` — `src/`, `config/`; `@Tester` — `tests/`; `docs/` read-only; `agent_docs/progress/` только append.
Одна цель = один этап = один PR, ветка `cursor/demo-d{N}-{краткая-цель}`.

## 3. Preflight облачного агента (первый шаг каждого этапа)

Агент обязан начать с проверки посылки и остановиться с внятным отчётом, если чего-то нет:

| Что проверить | Если отсутствует |
|---|---|
| `cloud_in/agent/AGENTS.md` и `rules.md` | стоп, `cloud_out/BLOCKED.md`: нет роли |
| `cloud_in/prompt.md` + `HANDOFF.md` | стоп, `cloud_out/BLOCKED.md` |
| файлы из раздела «Inputs» промпта (аудио, артефакты, конфиги) | стоп, перечислить недостающее по именам |
| секреты этапа (`GEMINI_API_KEY` для D3, `HF_TOKEN` для загрузки моделей) | пропустить только зависящие шаги, остальное довести |
| отсутствие `eval/` и `.env` в посылке | если оказались в `cloud_in/` — не читать, отметить в отчёте |

## 4. Что нужно подготовить до первого handoff

| Пункт | Действие | Кто |
|---|---|---|
| `cloud_in/` и `cloud_out/` видны облаку | сейчас оба каталога в `.gitignore` (строки «Future exchange»), а обменник работает только через git — снять ignore именно с них, `prompts/` оставить локальным | человек, одна правка `.gitignore` |
| Золото `eval/` вне индекса | `git rm --cached eval/*.json` (файлы остаются на диске) — решение Q4 | человек, до первого handoff |
| `cloud_in/agent/AGENTS.md` + `rules.md` | продуктовая роль: стек демки, шлюзы, бюджеты, запреты | @Planner в Фазе B |
| `cloud_in/inputs/` этапа | только то, чего нет (или не должно быть) в git как продукт: `STACK.md`, аудио-клипы, эталонные артефакты. Контракты и инструкции остаются в `agent_docs/` — облако их читает из репо. **`docs/research_results/` в посылку не кладём и облаку не указываем** | @Planner + человек при pack |
| Секреты в дашборде Cursor | `HF_TOKEN`, `GEMINI_API_KEY`. **`QWEN_API_KEY` в облако не передаём** | человек |
| Spend limit и модель прогона | по чек-листу скилла `cloud-agent-setup`, пункты 1–5 | человек |

Окружение (`uv sync`, ffmpeg, префетч моделей) облачный агент поднимает сам по `cloud_in/agent/AGENTS.md`, как это делалось в исследовании: `.cursor/` остаётся локальным и в облако не едет.

## 5. Разделение LLM: облако и локально

| Контур | Модель | Ключ | Роль |
|---|---|---|---|
| Облако (шлюзы D2, D3) | Gemini 2.5 Flash | `GEMINI_API_KEY` в дашборде | проверенный потолок качества из 3c |
| Локально (ручной шлюз, профиль `dev`) | Qwen3-8B Q5 через llama.cpp | ключ не нужен, модель локальная | сверка «а что даёт локальная модель», задел под `prod` |
| Демка в проде-демо | Gemini через серверный ключ | `GEMINI_API_KEY` | ТЗ §3: облачная LLM по серверному ключу |

Из этого следует: `local_llama` — не заглушка, а рабочий компонент, который реализуется на этапе D3 и используется в профиле `dev` локально. Адаптер `openai_compat` остаётся необязательным (пригодится, если появится сторонний провайдер), в облаке не настраивается.

## 6. Бюджеты облачного прогона (в `cloud_in/agent/AGENTS.md`)

| Блок | Лимит |
|---|---|
| Установка пакетов | ≤2 попытки на семейство, затем блокер в `cloud_out/` |
| Прогон ASR на клипах | ≤3 запуска за этап; полный 24-минутный файл в облако не попадает |
| Вызовы Gemini | ≤20 за прогон (12–15 глав + саммари + отчёт), ответы кэшировать в артефакты |
| Локальная LLM в облаке | запрещена (нет смысла и нет железа) |
| Тяжёлый прогон 15-минутного среза | только D5, ≤2 запуска |
| Провал шлюза | не менять порог, а писать `cloud_out/gate_D{N}.md` со статусом FAIL и остановиться |

Секреты никогда не печатаются и не коммитятся; каждый вызов API фиксируется в отчёте как «провайдер + зачем», без ключа.

## 7. Локальный ручной шлюз

Человек проверяет на своей машине (16 ядер, 27 ГБ) и на полной записи `data/voice 002.m4a` (24,5 мин), которой в облаке нет:

1. **D1** — послушать 2–3 фрагмента (включая тихие) и прочитать транскрипт; при желании WER/CER против `eval/`.
2. **D2** — прочитать оглавление: можно ли по нему найти нужный момент встречи.
3. **D3** — прочитать саммари и ключевые моменты; при желании сравнить Gemini и локальный Qwen на одних главах.
4. **D4** — пройти сценарий в браузере, проверить лимиты, прогресс и удаление по TTL.

Итог — строка в `agent_docs/progress/stage_D{N}.md`: `HUMAN_GATE: PASS|FAIL` + причина одной фразой.

## 8. Параллельные этапы

Допустимо вести одновременно этапы на разных файлах и данных: D2 (`chunking/`, `insights/titles.py`) и D4 (`web/`, `jobs/`) — оба на артефактах-фикстурах из `cloud_in/inputs/`. Условия: непересекающиеся списки файлов в промптах, разные ветки, отдельная посылка `cloud_in/` под каждый handoff (обменник плоский, поэтому два параллельных этапа = два последовательных pack'а с фиксацией, какой промпт ушёл в какую ветку).
