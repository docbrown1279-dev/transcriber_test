## 1. Что делаем

Приложение-протоколист совещаний профиля `demo` из `docs/dev_specs.md` §3 и §7: загрузка аудио → пайплайн → страница результата с саммари, ключевыми моментами и таймкодами.

Разработка идёт **этапами, повторяющими исследование**: каждый этап — один облачный агент, один PR, один автоматический шлюз в облаке и один ручной шлюз локально. Профили `dev` и `prod` не реализуются, но все точки расширения из ТЗ появляются сразу как заглушки за интерфейсами (см. [архитектуру](draft_architecture.md) §4).

## 2. Стек демки (взят из исследования, не пересматривается)

| Слой | Решение | Откуда |
|---|---|---|
| Нормализация | ffmpeg → 16 кГц mono WAV; linear `volume=` на `normalized.wav` если RMS < −30 dBFS; **VAD-only** `vad_input.wav` = `dynaudnorm=f=150:g=7:p=0.9` (C3) | 1e, 2b, D1 dual-path |
| Шумоподавление | **не применяем** | 1a/1b — пропуск |
| VAD | Silero VAD ONNX на `vad_input`; `min_speech_ms=400`; TEN-VAD fallback в дырах по умолчанию **выключен** | 1f2, D1 coherence |
| Диаризация | WeSpeaker на `normalized.wav` (без компрессии); premerge gap ≤1,0 с; same-speaker gap ≤0,8 с; absorb turn <2,5 с | 1f, 1f2, D1 C3+agg |
| ASR | GigaAM `v3_rnnt` (CPU torch), ≤25 с/сегмент; **per-turn** linear gain на срезах | 1e, 2b, D1 dual-path |
| Словарь | только **предложения** замен, без молчаливой правки; в демке пустой базовый словарь | 2b, план §«Потом — словарь» |
| Чанкинг | вариант **C**: packing разных спикеров (gap ≤2 с) + эмбеддинги `rubert-tiny2`, порог 0,70 | 2b conclusions |
| Заголовки глав | LLM, промпт **P1** (title + пункты одним вызовом), ≤10 слов, без «обсуждение …» | 3 |
| Инсайты + отчёт | LLM: extract по главам, затем один вызов саммари/отчёта после merge | 3b, 3c |
| LLM демки | Gemini 2.5 Flash в облаке и в демке; локальный Qwen3-8B Q5 (llama.cpp) для локальной сверки и задела под `prod` | 3c |
| Таймкоды | только копирование границ ASR-сегментов; LLM время не генерирует | план, «Таймкоды глав» |
| UI | FastAPI + Jinja2, серверный рендер, прогресс через polling/SSE | ТЗ §3 |

Расхождения ТЗ и исследования разобраны в §6 — решения приняты пользователем, а не выбраны самовольно.

## 3. Этапы

Нумерация `D0…D5`. Каждый этап: цель → что делает облако → шлюз облака → ручной шлюз человека → артефакт для следующего этапа.

### D0 — каркас и заглушки (нет качественного шлюза)

- `pyproject.toml` (uv), `src/transcriber/`, `tests/`, `config/{demo,dev,prod}.yaml` по §6–§9 ТЗ.
- Все интерфейсы пайплайна (порты) + рабочие реализации-«ничего не делает» и `prod`-заглушки, падающие понятной ошибкой.
- Оркестратор пайплайна на файловых артефактах, модели ещё не подключены.
- Инфраструктура обмена: `cloud_in/agent/{AGENTS.md,rules.md}` (роль продуктового облачного агента), `cloud_in/inputs/` первого этапа, `cloud_out/` пустой.
- **Шлюз облака:** `pytest`, `ruff`, `mypy`, `bandit` зелёные; `python -m transcriber.pipeline --dry-run` проходит цепочку на фикстурах-артефактах.
- **Человек:** ревью структуры и контрактов, merge.

### D1 — голос → транскрипт (шлюз №1 пользователя)

- Нормализация, VAD, диаризация, ASR, склейка/дыры, `suggestions.json` (пустой в демке).
- Облако: **полный** текстовый прогон packed `voice_002.m4a` → артефакты в `cloud_out/`; автопроверки этапа (в контракте названы **G1**: ru-ratio, латиница = 0, схема, …). `G1` — не отдельный этап, а чеклист внутри D1.
- **Человек локально:** скачивает результат, слушает фрагменты, читает транскрипт; при желании WER против `eval/`.

### D2 — чанкинг и названия глав (шлюз №2 пользователя)

- Вариант C, эмбеддинги, LLM-заголовки промптом P1.
- Артефакт: `chapters.json` (главы + `title`).
- **Шлюз облака:** плотность 0,4–0,8 главы/мин, длины 45–180 с (нарушения — предупреждения), заголовок ≤10 слов, без штампов, уникальность; агент отдельно читает главы и пишет вердикт осмысленности в отчёт этапа (G2).
- **Человек локально:** читает оглавление на полной записи, оценивает пригодность как ориентир.

### D3 — отчёт LLM (шлюз №3 пользователя)

- Extract по главам (`key_points` / `actions` / `open_questions` / `src`), затем один вызов: саммари + ключевые моменты с таймкодами.
- Артефакты: `insights.json`, `report.json`, `report.md`.
- **Шлюз облака:** clock-gate (все таймкоды дословно из `chapters.json`, mismatch = 0), каждый `key_point` привязан к `src`, нет выдуманных чисел вне текста, объём ключевых моментов 5–12; вердикт агента об осмысленности (G3).
- **Человек локально:** читает отчёт на полной записи, сравнивает со своим представлением о встрече.

### D4 — веб-интерфейс демки (шлюз №4 пользователя)

- Загрузка → страница прогресса → страница результата → скачивание; лимиты ТЗ §3 (1 запрос/IP/сутки, 1 одновременная задача, TTL 24 ч).
- **Шлюз облака:** `pytest` (юнит + E2E на клипе), `GET /healthz` 200 с состоянием компонентов, лимиты отдают 429, TTL-уборка удаляет артефакты (G4).
- **Человек локально:** проходит сценарий в браузере на реальном файле.

### D5 — готовность демки к железу (после четырёх шлюзов)

- Docker-образ; прогон под `--cpus=2 --memory=8g` на 15-минутном срезе; замер wall time и peak RSS по этапам; при промахе — снижение лимита до 10–15 мин (ТЗ §3, §10).
- **Шлюз облака:** отчёт производительности + отсутствие OOM; **человек:** решение о публикации демки.

### Зависимости и параллелизм

D0 → D1 → D2 → D3 → D4 по данным, но не по календарю: D2/D3/D4 можно вести параллельными облачными агентами на **эталонных артефактах-фикстурах** (текст GigaAM без золота из `docs/research_results/reports/1f/baseline/gigaam_v3_on_pyannote/`, копируется в `cloud_in/inputs/` при pack). Реальная сцепка проверяется, когда предыдущий этап смёржен.

## 4. Что переносится в `prod` только как заглушка

`pyannote`-диаризация, late chunking (Jina, вариант D), доменные словари с обучением, ручное редактирование, аудиоплеер с подсветкой, экспорт PDF, гибрид C→D. Для каждого — порт, регистрация в фабрике и тест «ключ есть в реестре, вызов даёт понятную ошибку `not available in profile demo`».

Исключение: локальная LLM (Qwen3-8B через llama.cpp) реализуется по-настоящему на D3 — она нужна для локальной сверки с Gemini и заранее закрывает главный компонент `prod`.

## 5. Риски

| Риск | Митигация |
|---|---|
| torch (рантайм GigaAM) не влезает в 7–8 ГБ вместе с веб-процессом | ASR в отдельном процессе, память освобождается после этапа; замер RSS в D1 и D5 |
| 15 мин аудио на 2 vCPU дольше приемлемого | ранний замер в D1; при промахе лимит 10 мин (ТЗ разрешает) |
| TEN-VAD: Apache-2.0 с non-compete Agora | выключен по умолчанию, отдельный флаг, юридическая проверка до публичного демо |
| Золото `eval/` лежит в git и технически видно облаку | снимаем с трекинга до первого handoff (Q4), в `cloud_in/` не кладём, все облачные шлюзы работают без золота |
| Качество инсайтов 8B/Flash — черновик (вывод 3c) | UI формулирует результат как черновик протокола, не итоговый документ |
| Неконтролируемые расходы на LLM API | лимиты вызовов в `AGENTS.md`, серверный ключ, 1 задача/IP/сутки |

## 6. Принятые решения по спорным точкам

| № | Вопрос | Решение пользователя |
|---|---|---|
| Q1 | откуда облако берёт аудио и фикстуры | не коммитим в `tests/fixtures/`: перед каждым этапом всё нужное кладётся в `cloud_in/inputs/` по правилам handoff, облачный агент проверяет комплектность на старте (preflight) |
| Q2 | эмбеддинги чанкинга (`bge_small_onnx` в ТЗ vs `rubert-tiny2` в 2b) | `rubert-tiny2` 0,70 как проверенный; `bge-small` — сменный бэкенд-заглушка за портом |
| Q3 | провайдер LLM | в облаке Gemini 2.5 Flash; локально Qwen3-8B через llama.cpp; `QWEN_API_KEY` в облако **не передаём** |
| Q4 | золото `eval/` лежит в git | снять с трекинга (`git rm --cached eval/*.json`, файлы остаются на диске) до первого облачного этапа |
| Q5 | облачные правила и окружение | `.cursor/` остаётся локальным; роль и нормы для облака кладём в `cloud_in/agent/`, путь указывается в промпте |
| Q6 | словарная коррекция в демке | модуль предложений с пустым базовым словарём: артефакт `suggestions.json` есть, текст транскрипта не правится |

Из Q1 и Q5 следует одна обязательная правка репозитория: каталоги `cloud_in/` и `cloud_out/` сейчас в `.gitignore`, а обменник работает только через git — ignore нужно снять именно с них (`prompts/` остаётся локальным). Подробности и полный чек-лист подготовки — в [облачном процессе](draft_cloud_workflow.md) §4.

Из Q3 следует, что `local_llama` — не заглушка, а рабочий компонент профиля `dev`, реализуемый на этапе D3.
