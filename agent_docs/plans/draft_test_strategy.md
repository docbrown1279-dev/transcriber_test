
# Черновик стратегии тестирования (Фаза A)

**Статус:** draft, ждёт ✅.
**Связано:** [roadmap](draft_demo_roadmap.md), формальные пороги — [`contracts/quality_gates.md`](../contracts/quality_gates.md).

---

## 1. Четыре уровня проверки

| Уровень | Кто гоняет | Что ловит | Детерминизм |
|---|---|---|---|
| Юнит | облако + локально, каждый PR | арифметика и границы: gain, склейка turn'ов, дыры, резка 25 с, packing, косинус, лимиты, TTL, ru-ratio | полный, без моделей и сети |
| Контрактные | облако + локально | JSON-артефакты против pydantic-моделей и эталонных фикстур | полный |
| Интеграционные | облако | цепочка на клипе ~85 с с реальными моделями | недетерминированные тексты — проверяем инварианты, не строки |
| Шлюз качества этапа | облако (авто) + человек (вручную) | пригодность результата: русская речь, осмысленность названий и инсайтов, работающий UI | частично субъективный |

Правило, унаследованное из правил `@Tester`: тест никогда не ослабляется ради зелёного прогона; проваленный шлюз — это отчёт `agent_docs/reports/gate_D{N}.md` со статусом FAIL, а не подкрученный порог.

## 2. Фикстуры

Тяжёлые входные данные в репозиторий не коммитятся: они приезжают в `cloud_in/inputs/` при каждом handoff (решение Q1), а облачный агент проверяет комплектность на старте.

| Фикстура | Что | Откуда |
|---|---|---|
| `cloud_in/inputs/audio/*.m4a` | 1–2 клипа ~85 с для интеграции и шлюза D1 | вырезка из `data/voice 002.m4a`, копия при pack |
| `cloud_in/inputs/artifacts/transcript_*.json` | эталонный транскрипт для D2–D4 без запуска ASR | `docs/research_results/reports/1f/baseline/gigaam_v3_on_pyannote/` |
| `cloud_in/inputs/artifacts/chapters_*.json` | 12–14 глав для D3/D4 | результат D2, возвращается через `cloud_out/` и переиспользуется при следующем pack |
| `tests/fixtures/llm/*.json` | записанные ответы LLM («кассеты») — маленькие, в git | сохраняются при живом прогоне шлюза |
| `tests/fixtures/artifacts/*.min.json` | 2–3 сегмента и 1–2 главы для юнит- и контрактных тестов — маленькие, в git | вырезка вручную, без осмысленного текста встречи |
| `eval/test_*.json` | человеческое золото | **только локально**, в `cloud_in/` не кладём, из индекса git снимаем (Q4) |

Отсюда правило для тестов: путь к тяжёлым фикстурам берётся из переменной окружения (`TRANSCRIBER_FIXTURES_DIR`, по умолчанию `cloud_in/inputs/`), интеграционные тесты помечены `@pytest.mark.requires_inputs` и **пропускаются** при отсутствии данных, а юнит- и контрактные тесты обязаны быть зелёными на одном git — без аудио и без сети.

Живые вызовы LLM — только в шлюзовом прогоне этапа (Gemini, лимит по бюджету); обычный `pytest` работает на кассетах и не тратит API.

## 3. Автоматические шлюзы в облаке по этапам

Пороги и формулы — в [`contracts/quality_gates.md`](../contracts/quality_gates.md); здесь смысл.

**D0.** Preflight посылки (`cloud_in/agent/`, `prompt.md`, перечисленные inputs на месте) — при недостаче стоп и `cloud_out/BLOCKED.md`; затем `pytest`, `ruff check src/`, `mypy src/`, `bandit -r src/ -ll` зелёные; реестр компонентов содержит все `prod`-заглушки, и каждая даёт `ComponentUnavailableError`, а не падает как попало; сухой прогон пайплайна на фикстурах-артефактах.

**D1 (голос).** Доля русских слов ≥ 0,90 по всему транскрипту; латиница в сегментах = 0; схема артефакта валидна; дыры ≥0,5 с и пустые сегменты перечислены (пустой сегмент — допустимое состояние, не ошибка); wall time и peak RSS записаны в отчёт. Дополнительно агент читает 3–5 фрагментов и подтверждает, что это связная русская речь, а не набор слов.

**D2 (главы и названия).** Плотность 0,4–0,8 главы/мин; главы <45 с и >180 с — предупреждение с перечислением, а не провал; `title` ≤10 слов, уникален, не начинается со штампов «обсуждение / обсудили / говорили о / совещание по»; таймкоды глав дословно совпадают с границами исходных сегментов. Затем агент читает каждую главу и её название и пишет вердикт: попадает / общее / мимо, с числом «мимо» ≤ 1 из 12–14.

**D3 (отчёт).** Clock-gate: каждый таймкод в `insights.json` и `report.json` присутствует в `chapters.json` дословно, mismatch = 0; каждый `key_point` имеет непустой `src`; числа в пунктах встречаются во входном тексте главы (проверка подстрокой по цифрам — защита от выдуманных «300 МВт»); ключевых моментов 5–12; ни одного пункта, начинающегося со штампов. Затем вердикт агента: сколько пунктов проверяемые факты, сколько — вода.

**D4 (веб).** `pytest` включая E2E: загрузка клипа → прогресс → страница результата → скачивание; `GET /healthz` = 200 и перечисляет состояние компонентов; второй запрос с того же IP в сутки → 429; файл больше лимита → 413/понятная ошибка; аудио длиннее лимита → отказ до пайплайна; TTL-уборка удаляет каталог задачи; в логах нет текста транскрипта и нет значений ключей.

**D5 (железо).** Прогон в Docker с `--cpus=2 --memory=8g` на 15-минутном срезе: без OOM, отчёт по wall time и peak RSS по этапам, вывод «лимит 15 мин выдерживаем / снижаем до 10».

## 4. Ручные шлюзы человека (локальная ветка)

Каждый — на полной записи `data/voice 002.m4a`, которой в облаке нет.

1. **D1.** Прослушать 2–3 участка (включая тихие) и сверить с транскриптом; при желании прогнать WER/CER против `eval/`. Ожидание из 1e: ~0,38 µWER — это уже известный уровень, а не дефект реализации; смотрим, не стало ли хуже.
2. **D2.** Прочитать оглавление целиком: можно ли по нему найти нужный момент встречи.
3. **D3.** Прочитать саммари и ключевые моменты: есть ли конкретика, нет ли выдуманных поручений и цифр (урок 3/3c — модель склонна к однострочникам и штампам). Здесь же сверка Gemini (облачный прогон) и локального Qwen3-8B на тех же главах.
4. **D4.** Пройти сценарий в браузере на реальном файле, проверить прогресс, скачивание и удаление по TTL.

Итог человек фиксирует строкой в `agent_docs/progress/stage_D{N}.md`: `HUMAN_GATE: PASS|FAIL` + одна фраза причины.

## 5. Регрессия между этапами

После merge каждого этапа облачный агент следующего этапа обязан прогнать **все** предыдущие юнит- и контрактные тесты, а шлюзы D1–D3 переиспользуются как код в `src/transcriber/quality/`: это библиотека проверок, вызываемая и из тестов, и из CLI (`python -m transcriber.quality check-transcript …`). Так «проверка на 90 % русских слов» не остаётся разовым скриптом облачного прогона.

## 6. Чего в тестах не делаем

Не сверяем тексты LLM дословно (недетерминированы); не считаем WER в облаке (нет золота); не гоняем полный 24-минутный файл в облаке; не гоняем локальную LLM в облаке; не тестируем `prod`-компоненты по существу — только контракт «зарегистрирован и даёт понятную ошибку»; не тащим в демку тестовый фреймворк исследования (`scripts/stage*`).
