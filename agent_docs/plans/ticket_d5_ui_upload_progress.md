# Тикет: UI — preload аудио + починка индикатора прогресса

**Статус:** OPEN (backlog) — staging preload + dual ETA labels landed with TTFT merge (2026-09-13); **остаток: вялый poll статусов в UI**  
**Приоритет:** средний (UX)  
**Ветка (когда откроем):** от `main`, напр. `cursor/d5-ui-upload-progress`  
**Не цель:** warmup моделей WeSpeaker/GigaAM (H0 закрыт как нерелевантный на малых моделях)

---

## Зачем

1. **Preload аудио.** Лимит демо ~**150 МБ**. Пока пользователь выбирает файл и ещё не нажал «Обработать», можно уже качать на сервер — выигрыш **>2 с** на тяжёлом файле (часто больше на медленном uplink).
2. **Индикатор прогресса.** Уже чинили (parked wip `8ee9c6f` — live TOC / progress ETA), потом **откатили**: при параллельной обработке терялись куски артефактов/событий. Нужна аккуратная починка **без** возврата сломанного parallel TOC.

---

## Scope

### A. Staging preload

1. На `change` у `<input type=file>` — `POST` во **staging** (`var/staging/` или аналог), не в `var/jobs/<id>/`.
2. Перед новой загрузкой в staging — **очистить** предыдущие файлы (не копить).
3. «Обработать» — создать job и **перенести/привязать** staging → `upload.*` job’а (без повторной заливки с клиента, если файл уже на сервере).
4. TTL / очистка staging при рестарте и при уходе со страницы — по возможности; минимум: clear-on-next-select.
5. Лимит размера тот же, что у job upload; ошибки размера/типа — сразу в UI.

### B. Progress indicator

1. Разобрать текущий poll `/jobs/{id}/events` + `overall_progress_pct` — где врёт / залипает.
2. Не тащить целиком parked live-TOC из `8ee9c6f`. Вынуть только безопасные куски (ETA / % / elapsed), если они не завязаны на parallel writer.
3. Регрессия: **один** активный job на воркере (как сейчас) + сценарий «два вкладки / два job подряд» — события и артефакты не дырявые.
4. Не смешивать с file-split early UI в том же PR, если не нужно: split пишет early chapter отдельно.

### C. Backlog — вялое обновление статусов (2026-09-13)

Поле: счётчик elapsed ок; dual ETA и лейблы (`фрагмент N из M`, `глава K из T`) ок по смыслу; **UI обновляет статус с задержкой / рывками** (poll или редкие `StageEvent` во время длинной diar/ASR фазы). Финальная сборка артефактов при этом нормальная — **не чинить сейчас**.

Идеи на потом (не делать без отдельного тикета):
- чаще эмитить soft status во время длинных фаз; и/или
- на клиенте тикать ETA от `eta_*_sec` + `elapsed` между poll’ами;
- не залипать на устаревшем `message` активного stage.
