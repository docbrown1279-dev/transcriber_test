# Техническое задание на разработку системы распознавания и анализа речи

По итогам исследования возможностей распознавания и анализа речи docs/research_results
предлагается создать рабочую версию приложения

---

## Конфигурации системы: `dev` / `demo` / `prod`

**Статус:** draft v0.1  
**Область:** базовое разделение окружений и требований к пайплайну транскрибации и протоколирования совещаний.

---

## 1. Общая идея

Система должна поддерживать несколько профилей запуска:

```text
dev  — разработка, эксперименты, тесты, подбор параметров
demo — публичная облачная демонстрация с жесткими ограничениями
prod — боевой контур у заказчика, локальная обработка и приватность
```

Общий пайплайн во всех профилях концептуально один:

```text
входной аудио/видео файл
  ↓
нормализация аудио
  ↓
сегментация / диаризация
  ↓
нарезка на сегменты для ASR
  ↓
ASR
  ↓
словарная коррекция
  ↓
смысловой чанкинг
  ↓
обработка чанков LLM
  ↓
агрегация итогового протокола
  ↓
выдача результата
```

Но состав моделей, лимиты, UI и требования к производительности зависят от профиля.

---

## 2. Профиль `dev`

### Назначение

Профиль для разработки, исследований и тестирования.

Используется для:

- разработки пайплайна;
- сравнения библиотек;
- подбора порогов чанкинга;
- тестов ASR, диаризации, словарей, эмбеддингов;
- накопления тестовых данных;
- отладки промптов и LLM-агрегации;
- проверки режимов, которые потом могут попасть в `demo` или `prod`.

---

### Основные требования

```text
Максимальная гибкость.
Возможность экспериментировать.
Подробные логи и артефакты.
Режим GPU + проверка CPU-режима.
```

---

### Железо

- любое;
- возможен GPU;
- обязателен прогон в CPU-режиме, потому что `demo` и часть `prod` могут работать без GPU;
- ограничения ресурсов могут отсутствовать или быть мягкими.

---

### Что разрешено

- использовать тяжелые библиотеки, если они нужны для исследования;
- запускать оба варианта чанкинга:
  - `4.1` — объединение по спикерам + склейка по эмбеддингам;
  - `4.2` — late chunking через Jina;
- использовать локальные и облачные LLM;
- хранить сырые и промежуточные артефакты;
- включать debug-режимы;
- собирать подробную телеметрию.

---

### Модели и компоненты

| Компонент | dev-режим |
|---|---|
| Диаризация | pyannote, ONNX-аналоги, экспериментальные варианты |
| ASR | GigaAM_3, Whisper и другие варианты для сравнения |
| Шумоподавление | опционально |
| Эмбеддинги | любые тестируемые, включая более тяжелые |
| Late chunking | Jina, если доступен |
| LLM | локальные, облачные, гибридные |
| Словари | базовые, доменные, экспериментальные |

---

### Артефакты

В `dev` желательно сохранять:

```text
исходное аудио
нормализованное аудио
сырой ASR-текст
исправленный текст
лог словарных замен
сегменты диаризации
чанки
эмбеддинги или их метаданные
сырые ответы LLM
debug reasoning, если включен
итоговый протокол
метрики времени и памяти
```

---

### Критерии успеха для `dev`

- можно быстро запускать эксперименты;
- результаты воспроизводимы;
- видно, где именно деградирует качество;
- можно сравнивать разные подходы;
- есть метрики:
  - время обработки;
  - потребление памяти;
  - качество распознавания;
  - качество чанкинга;
  - качество протокола.

---

## 3. Профиль `demo`

### Назначение

Публичная или полупубличная демонстрация продукта в облаке.

Цель:

```text
быстро показать ценность продукта,
не перегрузить сервер,
не дать злоупотреблять бесплатным использованием.
```

---

### Железо

Ориентировочно:

```text
2–3 ядра CPU
7–8 GB RAM
без GPU
```



---

### Главные требования

```text
Максимально легкий стек.
Минимальное потребление памяти.
Предсказуемое время обработки.
Простой UI.
Защита от злоупотреблений.
```

---

### Ограничения

Рекомендуемые лимиты:

```text
длительность аудио: 15–20 минут
размер файла: до 200–300 MB
одна обработка в день на IP
одна одновременная задача
хранение результата: 24 часа
```

Если обработка 20 минут занимает слишком много времени, можно снизить лимит до:


10–15 минут


---

### Разрешенные компоненты

| Компонент | Что используем в demo |
|---|---|
| Диаризация | только легкий локальный вариант, желательно ONNX |
| ASR | GigaAM_3, CPU |
| Шумоподавление | только очень легкое или отключено |
| Словарная коррекция | да |
| Эмбеддинги | легкие, например `bge-small`  |
| Чанкинг | только вариант `4.1` |
| Late chunking | отключен |
| Локальные LLM | скорее всего отключены |
| Облачные LLM | да, через серверный API-ключ |
| Ручное редактирование | не используется |
| Интерактивный плеер | базовый или отсутствует |

---

### Запрещено или нежелательно в `demo`

- тяжелые нейросетевые шумодавы;
- локальные LLM;
- late chunking через Jina;
- длительное хранение пользовательских файлов;
- сложные интерактивные интерфейсы;
- фоновая дообучаемость;
- тяжелые зависимости (torch), если без них можно обойтись.

---

### Стратегия производительности

Основная идея:

```text
разбить аудио на части,
обрабатывать этапы параллельно там, где возможно,
выдавать результат прогрессивно.
```

Пример:

```text
1. VAD делит файл на части по паузам.
2. Первая часть уходит в диаризацию.
3. Вторая часть может параллельно готовиться к обработке.
4. После диаризации часть уходит в ASR.
5. После ASR — в словарную коррекцию.
6. После коррекции — в эмбеддинги и чанкинг.
7. Готовые чанки отправляются в LLM API.
8. Пользователь видит прогресс.
```

---

### UI для `demo`

Максимально простой:

```text
загрузка файла
  ↓
страница прогресса
  ↓
страница результата
```

Технически:

```text
серверный рендер
Jinja2-шаблоны
минимум JavaScript
SSE или периодический polling для прогресса
```

На странице результата:

- итоговый протокол;
- краткое саммари;
- ключевые моменты;
- таймкоды;
- при необходимости полный транскрипт;
- кнопка скачать результат.

---

### Критерии успеха для `demo`

- сервер не падает на 2–3 CPU / 7–8 GB RAM;
- 15–20 минут аудио обрабатываются за приемлемое время;
- пользователь понимает прогресс;
- результат выглядит ценно;
- нет неконтролируемых затрат на LLM API;
- нельзя легко обойти лимиты;
- файлы пользователей не хранятся долго.

## 4. Профиль `prod`

### Назначение

Боевое решение на сервере заказчика.

Главный приоритет:

```text
приватность,
автономность,
надежность,
качество протокола.
```

---

### Железо

Минимальный ориентир:

```text
6+ ядер CPU
16+ GB RAM
```

Рекомендуемый уровень выше, особенно если:

- совещания длинные;
- много транскрибаций в день;
- используется локальная LLM;
- нужен интерактивный режим;
- требуется ускорение обработки.

Возможно использование GPU:

```text
GPU не обязателен для старта,
но может сильно помочь для:
  - локальной LLM;
  - тяжелой диаризации;
  - обучения / LoRA / Unsloth;
  - массовой обработки.
```

---

### Главные требования

```text
Локальная обработка.
Отсутствие обязательных внешних вызовов.
Настраиваемые политики хранения.
Возможность адаптации под заказчика.
Стабильная работа на длинных записях.
```

---

### Разрешенные компоненты

| Компонент | Что используем в prod |
|---|---|
| Диаризация | локальная стабильная модель |
| ASR | GigaAM_3 локально |
| Шумоподавление | опционально, по качеству и ресурсам |
| Словарная коррекция | да, с доменными словарями |
| Эмбеддинги | локальные стабильные модели |
| Чанкинг | базово вариант `4.1` |
| Late chunking | опционально, только если Jina доступен локально и проходит по ресурсам |
| LLM | локальная модель или гибридный режим |
| Дообучение | возможно: LoRA / Unsloth / адаптация словарей |
| Ручное редактирование | желательно, этап 2 |
| Аудиоплеер | желателен |
| Экспорт | JSON / Markdown / PDF по необходимости |

---

### Производительность

Для протоколов совещаний скорость обычно не является главным требованием.

Типовой сценарий:

```text
заказчик загрузил запись
  ↓
система обработала ее за разумное время
  ↓
пользователь получил протокол и может его править
```

Допустимая задержка может быть выше, чем в демо:

```text
например, часовое совещание может обрабатываться 15–40 минут,
если это согласовано с заказчиком и не мешает рабочему процессу.
```

Узкое место:

```text
локальные LLM
```

Но объем текста обычно небольшой:

```text
120 слов в минуту
2 часа = 14 400 слов
примерно 30–45 тыс. токенов
```

Это рабочий контекст для локальных моделей, особенно если:

- текст обрабатывается не одним гигантским запросом;
- используется чанкинг;
- агрегация делается отдельным проходом.

---

### Будущие возможности `prod`

Во вторую очередь можно добавить:

#### Интерактивный режим

Не онлайн-транскрибация в реальном времени, а удобная работа с уже обработанной записью:

```text
аудиоплеер
  ↓
текст, синхронизированный с таймкодами
  ↓
подсветка сомнительных слов
  ↓
ручная замена слов
  ↓
предложение добавить замену в словарь
```

Желаемые функции:

- аудиоплеер для прослушивания исходной записи;
- опционально замедление воспроизведения;
- переход по таймкодам;
- подгрузка текста по временным меткам;
- подсветка слов с низкой уверенностью;
- выделение слова и замена;
- запрос: «добавить исправление в словарь?».

Это не стриминг и не обязательная часть первой версии.

---

### Конфигурации внутри `prod`

В будущем могут появиться разные прод-профили:

```text
prod-cpu-lite
prod-cpu-standard
prod-gpu-standard
prod-gpu-advanced
```

Но начинать лучше с одного базового:

```text
prod-standard
```

---

### Критерии успеха для `prod`

- система работает локально;
- внешние API не обязательны;
- данные не покидают контур заказчика;
- результат стабилен на длинных записях;
- можно вести доменные словари;
- можно исправлять текст;
- можно повторно запускать обработку;
- можно адаптировать качество под конкретные совещания заказчика.

## 10. Что важно не забыть

### Для `demo`

Главный риск:

```text
диаризация и ASR на слабом VPS могут работать слишком долго.
```

Поэтому нужно:

- делать нагрузочные тесты в Docker с ограничением CPU/RAM;
- измерять RTF;
- измерять пиковую память;
- при необходимости снизить лимит до 10–15 минут;
- параллелить обработку по частям аудио.

---

### Для `prod`

Главный риск:

```text
локальные LLM могут быть медленными на CPU.
```

Поэтому нужно:

- заранее определить допустимое время обработки;
- выбрать минимальную локальную модель, которая дает приемлемое качество;
- предусмотреть гибридный режим, если заказчик разрешит API;
- рекомендовать GPU при большом объеме задач.

---

### Для `dev`

Главный риск:

```text
увлечься экспериментами и потерять воспроизводимость.
```

Поэтому нужно:

- фиксировать версии моделей;
- сохранять конфиг запуска;
- хранить метрики;
- вести журнал экспериментов;
- периодически прогонять базовый тестовый набор.

## 11. Короткая формулировка по каждому профилю

### `dev`

```text
Максимальная гибкость для разработки и тестов.
Можно использовать тяжелые компоненты, экспериментальные модели и подробные логи.
Обязательно проверяем CPU-режим.
```

### `demo`

```text
Максимально легкая облачная демонстрация.
2–3 ядра, 7–8 ГБ памяти.
Только необходимые этапы.
Без локальных LLM и без late chunking.
Лимит 15–20 минут и 1 запрос в день на IP.
Простой UI на Jinja.
```

### `prod`

```text
Локальное боевое решение для заказчика.
Приватность и автономность.
Локальные модели.
Возможность адаптации, доменных словарей и дообучения.
Позже — интерактивный просмотр и редактирование.
```
