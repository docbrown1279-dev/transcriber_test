## Этап 2b — чанкинг

Вход: неизменные `results/asr/2/gigaam_v3_rnnt/meeting_sample.json` и `results/chunking/2/attempt_2_chunks_titled.json`. Если их нет — стоп. Не восстанавливать их новым прогоном.

### Протокол фиксации склейки

Схема [`docs/schemas/chunk_merge_log.schema.json`](schemas/chunk_merge_log.schema.json):

- каждая склейка — отдельный `op`: `source_ids` (только подряд), `start`/`end`, `old_titles[]`, `new_title`, `reason`;
- после прохода `leaf_ids_covered` == `0..n-1`, без дыр и дублей, иначе проход брак;
- запрещён one-shot JSON на 60+ названий;
- для A/B капы: **≤8** baseline-листьев в группе и **≤180 с**; для C/D число мелких ASR-листьев не ограничивать, но длительность также **≤180 с**;
- для LLM — **только соседняя пара** (да/нет + новый заголовок из двух старых).

### Таймкоды — только из исходного JSON

LLM **никогда** не генерирует, не округляет и не исправляет время. Для A/B листом считается готовый чанк из `attempt_2_chunks_titled.json`; для C/D — исходный ASR-сегмент из `meeting_sample.json`. Сначала определяется непрерывный диапазон листьев, затем:

- `start = source[first_source_id].start`;
- `end = source[last_source_id].end`;
- граница разрешена только **между** исходными ASR-сегментами;
- сегмент нельзя делить внутри: пословных таймкодов нет, интерполяция запрещена;
- пустой ASR-сегмент остаётся в покрытии и присоединяется к соседней главе детерминированно;
- в главе сохраняются `source_ids`, `start_source_id`, `end_source_id`, точный `timing_source` и `timing_method: source_boundaries`.

Отдельный валидатор проверяет, что время побитово/численно совпадает с `meeting_sample.json`, ids идут подряд, покрытие полное, а главы упорядочены. Qwen вызывается **после** фиксации диапазона и создаёт только `title`; её ответ не может менять ids или время.

Целевая плотность на эту запись (~24,5 мин): **8–20 глав** (черновик ≤1,5 заголовка/мин как потолок «ещё слишком мелко»). Старые 5–30 сверху слишком широкие. Предпочтительно ~12–18.

LLM на 2b — только уже выбранный **Qwen3-8B**, как на этапе 2, и только для заголовка/попарной проверки тематической близости. Генерация полного саммари и сравнение других моделей — исключительно этап 3.

### Гипотезы (четыре независимых опыта)

Порядок — промпт [`docs/prompts/stage2b_chunking.md`](prompts/stage2b_chunking.md):

1. **A. Эмбеддинг заголовков, без LLM-merge.** 63 названия уже есть. Соседний cosine по **title**, не по сырому тексту. Проверяет: проблема в модели, которая теряет id, или в том, что соседние названия не про одну тему. ≤3 порога. Капы как выше.
2. **B. Попарный LLM.** Тот же 8B: «две метки — одна тема?». Слайд по списку, лог `op`. Не саммари 16 минут. Решение модели влияет только на объединение соседних ids; время всё равно копируется из исходных границ.
3. **C. Pack across speakers.** Вопрос–ответ — одна тема: единица может брать соседние **разные** спикеры при gap ≤2 с. Потом tiny2 adjacent **один** size/threshold (старт 40–80 / 0,70). Новая схема packing, не четвёртый порог той же.
4. **D. Late chunking — обязательный независимый опыт 2b.** Первичный кандидат: `jinaai/jina-embeddings-v3` (~570M, 8192 токенов, мультиязычный), потому что для него опубликована исходная реализация late chunking. Альтернативы для отдельного последующего прогона: `Alibaba-NLP/gte-multilingual-base` (305M, 8192), `BAAI/bge-m3` (568M, 8192), `Qwen/Qwen3-Embedding-0.6B` (0,6B, 32K; long-context, но span-pooling для late chunking менее каноничен). Не делать bakeoff всех моделей в одном опыте.

Для D:

- атом = один исходный ASR-сегмент с точными `start/end`; короткие атомы можно паковать, но не резать;
- большое контекстное окно: **240 с**, ориентир 300–600 слов, overlap **60 с**;
- внутри окна получить контекстные token vectors, затем mean-pooling по span каждого атома;
- cosine считать между соседними атомами; для границы в нескольких окнах усреднять score;
- финальная глава: минимум **45 с**, целевой диапазон **75–150 с**, жёсткий максимум **180 с**;
- выбирать локальные минимумы cosine детерминированно (без LLM); если до 180 с сильной границы нет — брать самый глубокий минимум в допустимом диапазоне;
- ожидаемый выход — 8–20 глав, предпочтительно 12–18.

Окно 240 с — это **контекст для эмбеддера**, не размер главы. Оно обычно содержит 2–3 будущие главы и даёт каждой короткой реплике контекст с обеих сторон.

Не ретайтлить все 63, если packing не менялся. Отчёты: `results/reports/2b/`.

### Проверка результата

Для каждого A–D сохранить `review_sheet.json`: `method`, `chapter_id`, `start`, `end`, `title`, `source_ids`. Агент не выставляет качество сам себе и не читает `eval/`.

Проверяющий человек переносит оценки в локальный `eval/2b_chapter_review.json`:

- `timing_exact` — автоматическая проверка против исходного JSON;
- `boundary_quality`: 0 — граница внутри темы, 1 — спорно, 2 — явная смена темы;
- `title_relevance`: 0 — не соответствует, 1 — частично, 2 — соответствует интервалу;
- флаги `too_short`, `too_broad`, `missing_topic`.

Сравнение гипотез делать по человеческим оценкам при одинаковом числе глав, а не по мнению той же LLM.

## Этап 3 (потом) — разные LLM и полное саммари

Не этот прогон. Только когда главы 2b стабильны:

- сравнить разные LLM на одинаковых готовых главах;
- проверить названия и **полное саммари встречи**;
- отдельно проверять факты, решения и ответственных.

LLM не должна заново определять границы глав. Аудио в API по-прежнему нет. На 1a 7B Q4 уже выдумала «Разработчика» — мелкий Qwen не считать достаточным для итогового саммари.
